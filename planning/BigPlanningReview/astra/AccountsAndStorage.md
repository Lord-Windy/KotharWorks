# Accounts and storage — a reboot is not a new expedition

Keep **the account**, **the season**, and **the household in that season** distinct. An account signs in and survives resets. A season pins a frontier and its rules. A household owns that account's people, stores, skills and marks **in one season**. A bookmark, bot token or queued order must never silently switch to controlling the next household.

## Who is commanding whom?

- **Private slice:** provision two independent accounts and grant each a household. Use expiring, single-use invitation links redeemed for server-side browser sessions; issue an optional scoped bot token from the signed-in account. This makes cross-household tests real from the start. The lab uses synthetic account/household IDs and the same grants, with no credentials involved.
- **Open sign-ups:** use OIDC authorization-code login with PKCE through a maintained client or auth gateway. Verify issuer, audience, signature, state and nonce; map the stable `(issuer, subject)` pair to a local account. Display names and email addresses are not identity keys. This flow creates the same local session as an invitation. Sign-in grants no season membership by itself; joining an open season creates one household and its founding people as one idempotent transition.
- **Browser:** opaque, random session ID in a `Secure; HttpOnly; SameSite=Lax` cookie over HTTPS. Store its digest, account, expiry and revocation; require a CSRF token on changes. Logout invalidates the server-side session. Use OS cryptographic randomness for credentials; `SamRng` and the public world seed are for simulation.
- **Bot:** a signed-in owner can mint and revoke a random bearer token, displayed once. Store its digest, account, season, household, expiry and scopes such as `observe` and `command`. Authenticate it on every request and check that the targeted person/hold actually belongs to the grant. A watch-only token cannot issue orders. Both browser and bot share the household's command limits and writer order. Never put credentials into a replay, query string for ordinary API access, or chronicle.

## Proposed PostgreSQL schema map

One database, three app-owned schemas. These are logical tables and important keys, not migrations. Current rows answer “what is true now?”; the record answers “what input and consequences got us here?”

| Schema / relations | What to store and enforce |
|---|---|
| `wilds_id.account`, `identity`, `session`, `invite`, `bot_token` | Long-lived account key; unique provider identity; revocable credential digests. A bot grant references one season/household. Display/publication settings are separate from login identity. |
| `wilds_world.season`, `pack` | Open/closing/archived state, opening UTC, optional fixed closing second, seed, generator/rules/record versions, exact content digest and parameters, blueprint digest, last committed logical second, writer revision and next ordering counters. Store immutable pack bytes by digest. |
| `wilds_world.place`, `trail`, `claim` | Generated founding places/edges, travel costs and stable prototype keys; per-household remaining/reserved units at each starter site. The world graph is shared, extraction rights are explicit. |
| `wilds_world.household`, `person`, `skill` | One household per `(account, season)`; home site, publication consent, roster revision. A person belongs to exactly one household, with location, life state and queue revision. XP keyed by person and skill. |
| `wilds_world.job`, `reservation`, `due` | Ordered queue entries, blocked reason, running start/due times and pinned job definition; input/slot/pack-space claims tied to job. One running job per person (partial unique key); unique live queue position. Due key indexed by `(season_id, due_at, phase, stable_seq)`; a blocked queue has no wake timer. |
| `wilds_world.stack`, `building`, `progress`, `tech_unlock` | Store/pack containers and quantities; building site, type and state; cumulative counters such as timber unloaded. Unique `(household, tech_id)` and applicable building-slot constraints. Quantities and reserved amounts are nonnegative, reserved ≤ total. Moving goods balances the two containers. |
| `wilds_world.shipment`, `mark_entry` | Shipment identifies job, offer, goods and credit. Signed entries reference a unique cause (completed shipment, recruitment). A recruit checks spendable balance and debits atomically. Immutable credits give lifetime earned; sum of credits and debits gives spendable marks. One-off writ constrained per household and season. |
| `wilds_record.receipt`, `input`, `event` | Unique `(season_id, account_id, command_id)` → payload digest, stored status/receipt. Ordered normalized adjudicated commands and system inputs with logical time, stable order and simulation actor. Ordered outcomes with subject, audience, cause and structured payload. No session/token bytes. |
| `wilds_record.checkpoint`, `audience_feed` | Occasional canonical, versioned world snapshot at a record position, including active jobs and counters. Feed rows link visible events to a local household or public cursor; index `(season_id, audience_id, feed_seq)`. Publication uses an allowlisted projection. |

Use typed columns/FKs for owners, quantities, job state, due time and ordering. JSONB suits versioned order parameters and event details, not a whole mutable MMO save in one row. Scope game IDs and composite foreign keys by season; also enforce household ownership on person/queue/stock joins. Two accounts can each have a person called “Mara”. The DB runtime role has only the required rights in the Wilds schemas; keep versioned DDL and its migration role separate. `apps/samtechtree/` is a local precedent for app-owned schemas and numbered migrations.

## One commit boundary

1. The per-season writer holds its ownership lock, settles earlier deadlines, and checks account/grant and receipt. For a previously adjudicated ID return the stored response (same payload); a different payload is a conflict. Pre-auth failures and transient busy responses are not gameplay inputs.
2. Plan on the committed revision. In **one PostgreSQL transaction**, compare/update that revision, write changed rows and reservations, insert/delete due work, append the input and its receipt if this is a client command, append outcomes and audience feed rows. Persistent game-rule refusals such as `STALE_QUEUE` can store their receipt without gameplay effects. A scheduled completion has a stable job/due key rather than an HTTP receipt.
3. Commit, then install the plan in memory and acknowledge or publish. No durable commit means no acknowledged mutation. On uncertain commit outcome, recover by receipt or due key. A race for the last timber, or a double-click on “recruit”, cannot yield two credits or two people. If PostgreSQL is unavailable, pause the live writer and report unavailability; do not accept orders into a non-durable alternate world.

Keep full receipts and the input/outcome record for the live season; the polling feed may retain a shorter window. Archive the full record with finalized seasons. Canonical event/state hashes exclude account secrets, display time, pointer addresses and HTTP IDs unrelated to game state. Include game-level actor IDs, rule versions and stable ordering. Re-executing even the same seed with *different orders or different accepted times* is a fork, not a replay.

## Three different ways to start a process

| Operation | Contract |
|---|---|
| **Reboot the same season** | Acquire the season writer lock, load current rows and the pinned definitions, rebuild the deadline heap from durable due keys, then catch up in logical order to now. Reloading uses the already generated founding graph. A job neither disappears nor pays twice. |
| **Replay or fork in the lab** | Use genesis (or a verified checkpoint), the historical engine/rules and pack, and the normalized input tape up to a declared horizon. Compare events/state at that position. To fork, clone the checkpoint, change one policy/order/parameter, assign a new run ID and record parent and first divergence. Never write the experiment into the live season. |
| **Deliberately reset** | Announce a closing second **C**. Accept new orders only at times `< C`. Drain pre-existing work including completions due exactly at C; cutoff supersedes new queue starts at C. Cancel remaining work, release reservations without outputs, record `season.closed` and seal the final state/chronicle. Create a **new** season ID, seed and pinned manifest. Accounts and published archives survive; people, marks, tech, stores, queues and bot grants do not transfer. Old-season commands get `SEASON_CLOSED` (an authorized retry of a recorded ID can still read its old receipt). |

After an unexpected restart of a season whose closing second has already passed, catch up only to C and seal it by the same rule. This is observable fairness: a stopped server should not award another week's ore or cancel work that was due before the close.

**Preserve the ability to read what you save.** Keep numbered schema migrations with fixtures from the preceding version. Add compatible columns/readers first; pin live seasons to the rules they began with, and retain a build or compatibility runner for archived versions. Back up PostgreSQL, archived input tapes, immutable packs and blueprints. Rehearse a restore into a blank database: sign in to the same account, interrupt a known running job, resume, retry the last shipment, verify its one ledger credit and compare the state/journal with the uninterrupted fixture. A pretty chronicle is much more useful if you can still reproduce the decision it describes.
